# HQ state authority candidate — local only

Status: local design review accepted with constraints; actual-code and activation gates are separate. Dedicated HQ D1 plus authenticated Worker architecture; no deployment, resource creation, credential changes, or access to other application databases is authorized by this plan.

## Boundary and API
The Worker accepts only POST `/v1/claim`, `/v1/renew`, `/v1/commit`, `/v1/release`, `/v1/inspect`. No caller SQL, arbitrary URLs, raw prompts, code, private evidence, or provider credentials. JSON body is capped at 4096 bytes by streaming, requires exact operation-specific keys. IDs use `[A-Za-z0-9_-]{1,80}`; revisions/epochs are nonnegative safe integers; TTL is an integer 1000..300000 ms. Server SQL mutation-time clock controls expiry, not client time. No CORS or body/error logging; responses use no-store and generic errors.

`createAuthorityWorker({authorize, repository, goal})` returns a Worker handler. Missing authorization adapter or fixed scope fails closed. Adapter receives the Request and must return a verified `{subject, executionId, repository, goal}`; these must match configured repository/goal. Holder is derived from verified subject plus per-execution identity (not a reusable repository subject alone), never request JSON. The default export denies all requests. Tests inject synthetic verification, not a live credential scheme. executionId is a bounded opaque verifier-issued identifier, stable for an execution restart and distinct for another run/attempt. Receipts bind subject and executionId; a new execution cannot replay an older execution's key. Cross-run unknown outcomes require future authorized historical reconciliation, never blind retry under a new key. OIDC versus service-token verification remains a separate decision and approval gate. Possession of a client-supplied identity, approval flag, or claimed scope grants nothing.

Every request contains `jobId`; mutations also contain `idempotencyKey`, `expectedRevision`, `expectedEpoch`. Claim/renew add `ttlMs`; commit adds `state` and optional 64-hex `evidenceDigest`; release adds nothing. Inspect returns job counters/state and at most the latest 50 event metadata records (ordered by revision) with a truncation indicator, never raw input. This first slice stores only structured synthetic operational metadata. No DONE transition is enabled until a trusted independent verifier exists. Existing local JSON prototype is not replaced or migrated automatically.

## Data and consistency
Tables: `hq_jobs` (repository/goal/job composite key, state, revision, epoch, holder, expires_ms, last_operation, mutation_ms), `hq_events` (repository/goal/job/revision primary key, operation, state, epoch, timestamp copied from job mutation timestamp, evidence digest), `hq_receipts` (repository/goal/job/idempotency key primary key, principal, canonical operation/request digest including repository and goal, immutable result JSON). All SQL values are bound; counters guarded against safe-integer exhaustion. Mutations increment revision; every claim increments epoch. New claim explicitly expects revision=epoch=0 and yields revision=epoch=1, QUEUED. Released jobs retain epoch/revision history. Reclaim, release and renew preserve existing task state; only a brand-new claim initializes QUEUED. Expired jobs may be reclaimed at exact expiry using matching counters.

Use primary D1 binding (no read-replica sessions). A mutation is one `db.batch` transaction: (1) conditional job insert/update assigning fresh server-generated operation nonce, (2) event INSERT SELECT guarded by this nonce, (3) receipt INSERT SELECT guarded by this nonce, (4) SELECT receipt. Zero-row update is NOT an error: all dependent inserts must share the nonce guard, returning conflict with no changes when absent. Unique receipt conflict rolls back the entire batch. Concurrent same-key callers with differing body or principal must conflict even when a zero-row mutation subsequently observes another caller's receipt. On retry read existing receipt and compare principal+canonical request digest, returning exactly the prior response only on exact match. EVERY receipt return, including the final batch SELECT and ambiguous-failure lookup, revalidates principal/execution identity plus full canonical digest before exposing a response. After ambiguous write failure, read receipt from primary; return saved result if matching, known mismatch returns conflict; absent or unreadable receipt returns generic retryable unknown-outcome error, never assume nonexecution. Nonce is not reused between attempts. A replayed claim receipt is historical evidence, not proof that its lease remains active. No `changes()` dependence and no read-then-write exclusivity claim.

Claim allows missing or released/expired job with matching revision/epoch. Renew/commit/release require matching revision, epoch, verified holder and unexpired lease evaluated in SQL. Renew never shortens expiry (max current expiry, database now+TTL). Release clears holder/expiry but preserves epoch and increments revision. Commit follows QUEUED→RUNNING/BLOCKED/AWAITING_APPROVAL, RUNNING→VERIFYING/BLOCKED, VERIFYING→QUEUED/BLOCKED, BLOCKED→QUEUED; AWAITING_APPROVAL has no outgoing transition until trusted approval authority exists; it cannot claim completion or merge authority. Client timestamps and holder fields are rejected.

## Verification and activation gates
Local Node HTTP contract tests use fake DB only for validation paths. Transaction tests must run actual local D1 implementation via pinned Miniflare/workerd with disposable persistence, including two clients, rollback injection, stale/expired holder, replay conflict, restart and unknown outcome. Local D1 is not remote D1, cross-Actions execution, cloud auth or 24h evidence. No network auth/deploy test is claimed. No live database ID, deployment script, or deployment workflow is added; any local configuration has workers_dev=false.

Before activation: verify account plan/quotas and zero incremental cost; separately approve new dedicated DB, authenticated Worker endpoint, exact identity allowlist, credential or OIDC permissions, logging/retention/encryption policy, backup/recovery, deployment and remote migration. Existing other-application D1 resources remain untouched. PR9/Issue1 independent security gate still applies before autonomous writes. Public repository contains only source, sanitized specs and synthetic tests.
